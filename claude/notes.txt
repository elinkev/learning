part 2 - agentic loops 
	- api & sdk communication stack
		- my code - customer placing an order
		- anthropic sdk - library you install, wraps http complexity into simple method calls - waiter taking the order
		- claude api - handles api key auth and routes the requestt to the right model - kitchen ticket system
		- claude servers - run the language model, return structured response object - kitchen coooking the dish
	- messages.create() (5 parameters)- runs on every loop
		- model (required) - opus/sonnet/haiku
		- max_tokens (required) - if set too low, responses can get cut off, usefull to create distinct stop reason
		- system - persistent instructions that shape every response
		- tools - declere what actions claude is allowed to request
		- messages - full conversation history
	- what are tools - its not code, its a description
		- claude never sees your tool implementation it only sees - name, description, input_schema
		- claude decides what to call, your code decides how to execute it
		- when claude decides to run a tool, it responds with the tool_use_id, name, input, your code runs the function, result returned to claude as tool_result
	- every call to messages.create returns response object - 2 critical fields
		- stop_reason - why claude stopped 
			- end_turn - claude is done -> exit loop
			- tool_use - claude needs your code to act
				- this field has 3 important fields - id (unique), name (which tool claude wants to call), input (arguments for the tool)
			- max_tokens - response cut off -> handle carefully
		- content (array of blocks)
			- type: "text" - claude narration or final answer
			- type: "tool_use" - a tool claude wants to call
			* may contain both in single response
	- 4-step agentic loop pattern
		- 1) call messages.create() - send full conversation history and tool definitions. Claude sees everything accumulated so far
		- 2) check stop_reason - if its end_turn -> exit loop & return answer or if its tool_use -> continue to step 3
		- 3) execute all requested tools - find every tool_use block in content array, run each one, collect results
		- 4) append & loop back to step 1 - add claude response as Assistant message. Add all tool results as User message. Go to step 1
	- loop in action
		- 1) Messages: [user: "get weather in Tokyo and Paris"]
		- stop_reason: tool_use - claude requests get_weather('Tokyo'). Your code executes, returns result
		- 2) Messages: [user, assistant(Tokyo call), user(Tokyo result)]
		- stop_reason: tool_use - claude sees Tokyo done, requests  get_weather('Paris')
		- 3) Messages: [user, asst, user(Tokyo), asst(Paris call), user(Paris result)]
		- stop_reason: end_turn - claude has both results, generates final answer, loop finishes
		* claude figures on its on by reading the growing conversation history - it knows what was fetched previously and what is still missing
	- model-driven vs scripted automation
		- scripted example
			- 1) always search
			- 2) always calendar check
			- 3) always payment
			- order is hardcoded, cant addapt if a step returns unexpected data, you are the planner
		- model-driven example:
			- claude reads conversation context each iteration
			- decides what tool to call based on what it knows so far
			- calls one tool if thats all thats needed
			- addapts to unexpected results, exists as soon as the goal is met, claude is the planner
	- stop_reason - deep dive
		- tool_use - claude is NOT done, it needs to call a tool to continue, find all text_use  blocks, execute every one, append results, loop back
		- end_turn - claude is done. it has all information needed and produced final answer, break out of loop and return text content to user
		- max_tokens - response was cut off, claude hit the token limit before finished
	- 3 anti-patterns to avoid
		- text parsing for loop control - checking literal words like 'done' or 'finished' to exit loop, claude might say 'done' in step 1 but theres still a lot of steps, always use stop_reason
		- fixed iteration cap as primary control - primary exit must always be stop_reason == end_turn
		- keyword detection for tool routing - read the structured tool_use blocks in the content array, dont check if claudes text mentions a tools name to decide what to call
	- 7 things to know
		- loop pattern
		- tools are descriptions
		- stop_reason is the only control signal
		- messages array grow every iteration
		- model-driven means claude what to do next (claude is planner)
		- tool results go back as user role messages, wrapped in tool_result block with the matching id
		- use while true with safety counter as fallback, never fixed range as primary exit condition
part 3 - multi agent coordinator
	- why move from single to multi agent system - coordinator and subagents
		- a single agent can hold limited amount of context
		- each agent can be specialized - coding agent, research agent, writer reviewer etc
		- can run multiple agents simultaneously
		- multi agent only when constraints force it, most tasks can be handled with single agentic loop
	- hub-and-spoke architecture
		- hub - coordinator, all communication go throu coordinator
		- coordinator owns error handling, if subagent fails, its coordinators job to decide to retry or degrade gracefully
		- coordinator controls the flow - it decideds what context the subagents get, subagents dont know anything by themselves or can share info between themselves
	- isolated context
		- coordinator sees everything - original user request, all task tool calls, all tool result responses, full conversation with user
		- subagent - only sees its own system prompt that was passed by the coordinator
	- coordinator responsibilities
		- 1) decompose - break user request into subtasks with clear scopes for each agent
		- 2) delegate - issue task tool calls , one per sub agent, with fully specified prompt that the agent needs
		- 3) aggregate - collect all subagent responses and synthesize them into one coherent view
		- 4) evaluate - check quality and completeness - red-deleage if needed
		- 5) respond - deliver the final answer to the user, only after QA passes
	- the task tool (delegation
		- 1) coordinator emits task call - coordinators response includes a tool_use block with type: "task", target agent name, and a fully specified prompt
		- 2) sdk launches fresh claude instance - sdk spawns new claude session using target agents AgentDefinition - system prompt, tools, model settings
		- 3) subagent runs its own agentic loop - executs its own 4-step loop independently, including any tool calls it needs, until it reaches end_turn
		- 4) result returned as tool_result - the subagents final response come back into coordinators message history as a tool_result. Coordinators allowed_tools must include "Task"
	- parallel vs sequential excecution
		- parallel - coordinator returns two or more Task tool calls in single response, sdk launches all subagents simultaneously
		- sequential - coordinator issues one Task call per loop turn, waits for result before continuing, used when next step needs previous steps output
	- dynamic routing & work partitioning
		- dynamic routing - coordinator evaluates the request first, then decides which subagents to invoke
		- work partitioning - each subagent has distinct, non overlapping scope - no two agents work on the same data
	- iterative refinement & structured handoffs
		- iterative refinement (evaluate)- after receiving subagent response, coordinator checks QA, if something is not right - it re-delegates, not necessary to the same agent
		- structured handoffs - each finding from subagent must be tagget with source name, url, date
	- 5 anti-patterns
		- direct subagent-to-subagent communication - subagents never message each other
		- assuming inherited context - subagents start fresh
		- always-on full pipeline - triggering all subagents on every request regardless of complexity (dynamic routing)
		- overly narrow decomposition - splitting tasks so finely that subagents have overlapping scopes
		- raw text handoffs - passing unstructured text between agents with no source attribution (source, url, date)
	- 9 things to know
		- hub-and-spoke - coordinator and subagents
		- isolated context - subagents start fresh
		- responsibilities - decompose -> delegate -> aggregate -> evaluate -> respond
		- task tool - spawns subagents; coordinators allowed_tools must include "Task"
		- parallel execution - multiple task calls
		- sequential execution - one task per loop iteration
		- dynamic routing - only invoke subagents needed for request
		- structured harndoffs - every response from subagents need to be structured
		- iterative refinement - coordinator evaluates results, re-delegates if needed
part 4 - subagent config & context
	- raw api vs claude agent sdk
		- raw api - /messages endpoint, dirrect http call to claude servers, you manage every loop, every retry
		- sdk - python framework, built on top of raw api, gives structured building blocks - agents, tools, sessions
		- api = library, sdk = framework
	- task tool - how subagents get created
		- Task is a special built-in tool in the SDK, when coordinator calls it - sdk creates brand new agent instance
		- to use Task tool, coordinators allowed_tools MUST include "Task"
		- each task invocation creates new isolated subagent with no fresh context or memory of coordinators conversations
		- task description becomes subagents first user message
		- when subagent is finished, it responds back with "tool_result" in the coordinators messages array
	- AgentDefinition - 5 fields needed to spawn subagent
		- 1) name - agent identifier, used for logging and routing references
		- 2) description - what the agent does
		- 3) system_prompt - specialization instructions
		- 4) tools - list of tool definitions the agent can use - does not grant permission
		- 5) allowed_tools - list of tools that the agent can use, must be subset of tools, this is where minimum-tools design principle is enforced
	- minimum-tools design principle
		- wrong approach - every agent gets every available tool
		- correct approach - every agent gets tools only needed for the job
		- reasons why - security, reliability, cost
	- context passing
		- every subagent starts with zero context, coordinator must construct task description
		- what to pass - relevant facts, constraints, exact output format needed, prior subagent results if needed
		- what not to pass - entire conversation history
	- execution patterns - parallel vs sequential
		- sequential - use when task 2 needs tasks 1 output
		- parallel - use when tasks are independent 
		- mode determined by how you await - sequential awaits run one at a time, gather() awaits run concurrently
		- if task share NO data dependencies -> parallel is correct choice
	- fork sessions - same baseline, different paths
		- fork - divergent subagent spawn - spawn multiple subagents from same baseline context, each exploring different direction
		- use cases - brainstorming, a/b testing, hypothesis investigation
		- coordinator collects data from all forks and synthesizes final decision
	- goal-oriented prompt design
		- goal + output format - what u want subagent to product and in which format
		- constraints - what u want subagent to NOT do or access
		- dont specify exact tool sequence - leave the decision to claude
		- dont over-constrain execution - if u need to specify every step - use a script, not an agent
	- 6 anti-patterns
		- forgetting "Task" in allowed_tools - cant spawn subagents
		- giving all tools too all agents
		- dumping entire conversation history into task prompt
		- procedural prompts that specify every step - let claude decide execution path
		- unstructured data handoffs - raw text blobs with no metadata - always include source, date, confidence
		- treating parallel vs sequential as a style preference
	- 8 things to know	
		- Task tool creates isolated subagents - "Task" MUST be in coordinators allowed_tools
		- AgentDefinition has 5 fields - name, description, system_prompt, tools, allowed_tools
		- Minimum-tools principle - each agent only gets tools needed for the job
		- Subagents start black - pass all needed context: facts, constraints, format, prior results
		- sequential = await chain - parallel = asyncio.gather()
		- Fork = multiple subagents from same baseline, each exploring different direction
		- specify goals + output format - never specify exact tool call sequences
		- Structured metadata in all handoffs - source, date, confidence score for every cross-agent data transfer
part 5 - multi-step workflows
	- probabilistic vs deterministic compliance
		- probabilistic - relying on claude's judgement, you write the prompt, claude reads it and usually follows them, llms can be persuaded and edge cases exist
		- deterministic - using code-level checks, your code enforces the rule, claude's reasoning is irrelevant
		- claude is a language model - it can be persuaded. Given convincing context it might skip a step it would normally follow
		- production rule - safety critical constraints MUST be enforced deterministically in code
	- prerequisite gates 
		- gate - a check that blocks execution of tool B until tool A completes successfully 
		- implementation - wrapper function, before the downstream tool executes, the wrapper checks prerequisite state, if not satisfied - raises an exception
		- example - payment gate - payment_tool can only run after validate_card_tool returns success. Payment wrapper checks a flag set by validator - no flag - no payment
		* gates are code-enforced - claude cannot skip them
	- enforcement vs prompt guidance - when to use which
	 	- code enforcements - safety matters, compliance required, financial transactions, irreversible actions
		- prompt guidance - style preferences, tone and format, non-critical workflow ordering, mistakes that can be corrected
		* in other words - if action cannot be undone - use code enforcements
	- structured escalation handoffs
		- when to escalate - confidence drops below threshold, instructions are ambiguous, irreversible action is pending and agent isnt certain it should proceed
		- what to include in the handoff - summary of what was attempted, current state of the task, specific decision the human needs to make
		- format - structured json with 4 fields - action_requested (what human needs to do), context (what happened so far), options (available choices), recommended_action (what agents thinks is best)
		* escalation can never be vague, never pass "i need help" or "i got confused" for human review, always include actionable decision context
	- multi-concern decomposition example
		- single complex request "is this transaction safe?" 
		- coordinator splits this to 3 agents - fraud_check_agent, compliance_agent, risk_score_agent
		- each concern is isolated, each agent is specialized, each agent run parallel (unless they need each others outputs)
	- hooks in the agent sdk
		- hooks fire automatically around every tool call in the agentic loop
		- PreToolUse hook - fires before execution, usecases - block by raising exception, modify input before execution, log for auditing
		- PostToolUse hook - fires after execution, usecases - validate output, transform result before claude sees it, record the outcome for auditing
		- common use cases - audit logging, rate limiting (block over-called tools), output sanitization (strip sensitive data), schema validation (reject malformed input)
	- hooks code pattern
		- return None - allow the tool through unchanged, tool executes normally
		- raise Exception - block the call, tool will NOT execute, claude receives the error
		- return modified dict - override the input before execution, tool runs with your modified params
		* memorize these 
	- 5 anti-patterns
		- "dont run payment without validation" as prompt, trusting claude will follow it. Correct way is to use code gate that blocks payment_tool, until validate_card_tool passes
		- Claude calls tools out of oder - it thinks skipping a step is efficient. Correct way is to enforce order with prerequisite gate checks
		- escalating with "i need help" - human has no context to act. Correct way is using structured handoff - action_requested, context, options, recommended_action
		- registering hooks but ignoring their return values. Always propagate hook decisions - if a hook block, the tool must not run
		- decomposing depended concerns in parallel - agents that share state or need each others output. Only parallelize truly independent investigations
	- 7 thinks to know
		- probabilistic = claudes judgement (prompts), deterministic = your code (enforcement)
		- safety-critical constraints MUST be code-enforced
		- prerequisite gates block downstream tools until prerequisites succeed
		- irreversibility test - if a mistake cannot be undone -> code enforcement is required
		- structured escalation handoffs - always include action_requested, context, options, recommended_action
		- PreToolUse can block, modify, allow. PostToolUse can validate, transform, record
		- Multi-concert decomposition - parallelize independent concerns only, if concern B need A's output - use sequential
part - 6 
	- domain 1 - task 1.5 - sdk hooks & data normalization
		- transform messy tool data and enforce business policies with code
	- five tools five different formats
		- order system - "created_at": "1710633600" (unix timestamp)
		- customer system - "signup_date": "2025-04-01T10:00:00Z" (iso format)
		- shipping api - "ship_date": "03/17/2025" (US date format)
		- legacy database - "status": "200" (numeric status code)
		- modern api - "status": "active" (string status label)
		* claude has to interpret these values itself and usually it gets it right, but to enforce it you need to use hooks
	- what is data normalization
		- normalization means converting different formats into one format before claude sees them
	- why not just tell claude to use one format
		- prompt instructions are probabilistic, not deterministic, even 1% failure can cause problems
		- hook run after every tool call, works every time
	- transforming data after tool execution
		- claude calls get_order
		- tool returns raw data
		- PostToolUse converts unix timestamp into iso format, maps 200 status to "active"
		- claude receives clean result
	- transforming data before tool execution
		- claude calls process_refund(amount=$750)
		- PreToolUse hook intercept - it checks if amount > $500
		- blocks the tool execution - redirects to escalate_to_manager with full context
		- claude tells customer "escalated to a manager"
	- hooks vs prompts
		- hooks - deterministic
		- prompts - probabilistic
		- "guarantee" or "ensure" - use hooks, "encourage" or "prefer" - use prompts
		- examples when to use hooks - financial limits, data format requirements, compliance polices, acl
	- 5 anti-patterns
		- relying on prompts for data consistency - claude misinterprets unix timestamps, use hooks
		- blocking calls with no explanation - claude retries endlessly, always return clear message and alternative action
		- silently modifying data in hooks - debugging becomes impossible, always log all transformations and keep originals
		- using hooks for soft preferences - adds latency, reserve them for hard rules only
		- no redirect on blocked calls - claude will get stuck, always provide alternative - escalation, different tool, human handoff
	- 7 things to know
		- PostToolUse hooks normalize data into consistent formats
		- PreToolUse hooks block policy-violating calls 
		- hooks are deterministic, prompts are probabilistic (1-5% failure)
		- always explain why call was blocked
		- normalization targets - unix to iso, numeric to string statuses, regional to standard dates
		- keep hooks fast - they run on every tool call, no network calls
		- "guarantee compliance" answer is always hooks, not prompts
part - 7
	- domain 1 - task 1.6 - two fundamental approaches
		- prompt chaining - fixed sequential pipeline, each steps output feeds into the next one, used when steps are known upfront
		- dynamic decomposition - subtasks are generated depending on what is discovered on each step, used when scope is open-ended, cant predict full plan upfront
	- prompt chaining
		- fixed linear pipeline - steps designed upfront, step 1 output -> step 2 input -> step 3 input etc
		- best for structured, repeatable tasks - code review, data extraction, report generation
		- key advantage: focused context windows - each step sees only what it needs
		- example usage:
			- step 1 - multi file analysis (parallel) 
			- step 2 - integration (sequential) 
			- step 3 - summary 
	- dynamic decomposition
		- plan emerges from discoveries - you cannot write step 3 until u see step 1/2 results
		- best for open-ended investigation - "add tests to legacy codebase", "audit for vulnerabilities" - u know the goal but not the path
		- trade-off: higher cost, higher adaptability
		- example usage: 
			- phase 1 - map the structure (discovers: 12 modules, 4 have tests, 8 dont)
			- phase 2 - prioritise (of the 8 tests, which are critical? discovers: 3 critical modules - auth, payment, user-data) 
			- phase 3 - deep investigation (trace all code paths in the auth module. discovers: 15 code paths, 3 with complex branching)
			- phase 4 - generate tests (writes tests for all 15 paths)
			* this is impossible to plan because targets only emerge on phase 1-3
	- choosing the right approach
		- task structure - predictable, repeatable (prompt chaining, open-ended), expiratory (dynamic decomposition)
		- example - code review, data extraction (prompt chaining), "add tests to legacy code" (dynamic decomposition)
		- step dependencies - linear - output feeds next (prompt chaining), conditional - depends on findings (dynamic decomposition)
		- planning - full plan known (prompt chaining), plan emerges during execution (dynamic decomposition)
		- parallelism - often possible within steps (prompt chaining), less predictable - context-depended (dynamic decomposition)
		- cost - lower - fixed step count (prompt chaining), higher - steps may multiple (dynamic decomposition)
	- attention dilution - "lost in the middle"
		- LLMs process the beginning and end of long context more reliably than the middle part
		- impact on multi-file reviews - never send all files in single prompt
		- solution: per-pass decomposition - one file per prompt, then a separate integration pass
	- 5 anti-patterns
		- all files, one prompt - attention dilution trap, always decompose into profile passes
		- using dynamic decomposition for predictable tasks
		- using chaining for exploratory tasks
		- overly narrow subtask definitions - coordinator tasked with researching "create industries" decomposes it only into visual arts subtasks, something like fils or music is missed. Subtasks must cover the full scope
		- no cross-file integration pass - always add a cross-cutting integration pass
	- 6 things to know
		- prompt chaining - fixed sequential pipeline, use for predictable repeatable tasks
		- dynamic decomposition - adaptive plan, use for open ended investigation where scope is unknown
		- split large reviews into per-file passes plus a separate cross-file integration pass
		- attention dilution - LLMs pay less attention for content thats not in beginning or end of context
		- adaptive plans add, remove, reorder steps based on findings
		- chaining is cheaper, dynamic decomposition costs more
part - 8
	- domain 1 - task 1.7 - session
		- session - named, persistent record of conversation that you can return to later, all tool results are saved
	- why session matters
		- day 1 - analyze the codebase, claude builds mental model, identifies critical paths
		- day 2 - write tests based on what was found, claude already knows critical paths so no need to re-analyze again
		- day 3 - fix the bugs that the tests revealed, claude prior context is there, no need to re-explain everything again
	- named session flags
		- --session <name> (claude --session auth-refactor)
		- --resume (claude --resume auth-refactor)
	- when to resume and when to start fresh
		- resume - if the code didnt change, and still doing analysis 
		- resume with caution - if code changed between sessions
		- start fresh - context window mostly exhausted, or exploring new approach
	- stale context problem
		- when u resume a session, old tool results are still there, but files may have changed
		- solution 1 - after resuming the session, tell claude what was changed, works best if only few files were changed
		- solution 2 - start fresh with injected summary, ask claude to confirm or revise those findings on current codebase
	- fork_session - branch at decision point
		- fork_session - makes a branch of current session
		- can be used in parallel, useful to find multiple solutions for a problem then choose the best approach
		- each fork gets complete full history copy 
		- changes in fork A have no effect for fork B
		- forks run in parallel
		- original session remains unchanged, forking is non-destructive
	- when to use fork_session
		- comparing two refactoring strategies before committing
		- testing different testing approaches - unit vs integration focused
		- exploring alternative architectures after shared analysis without losing progress
		- never fork for simple linear tasks
	- session decision framework
		- if the code hasn't changed - resume
		- if the code has changed but context window is not exhausted - resume with caution
		- if the code has changed but context window is exhausted - start fresh
	- 5 anti-patterns
		- resuming code when files were heavily modified - you should start fresh or tell claude explicitly what changed
		- starting fresh when context is still valid - resume instead
		- never using named sessions - you lose all progress when terminal is closed
		- forking for simple linear tasks - only use forks when comparing alternatives in parallel
		- resuming with exhausted context - start fresh with injected concise summary of key findings
	- 7 things to know
		- --resume - resumes named session with full conversation history
		- stale context is biggest risk of resumption
		- mitigation 1: inform the resumed session about specific changes
		- mitigation 2: start a fresh session and inject a structured summary of prior key findings
		- fork_session - creates session branches from shared analysis baseline, use this to compare strategies in parallel
		- start fresh when code changed significancy, context is exhausted, or taking new direction
		- session management is all about preserving valuable analysis while avoiding stale context
part - 9
	- domain 2 - tool design & mcp integration
		- domain 1 is about how agents think and orchestrate
		- domain 2 is about how agents act - the tools they use
	- domain 2 - five tasks
		- task 2.1 - tool interfaces
		- task 2.2 - structured error responses
		- task 2.3 - tool distribution
		- task 2.4 - mcp servers
		- task 2.5 - built-in tools
	- task 2.1 - descriptions are everything
		- tools are descriptions, claude does not read its implementation
	- the misrouting problem
		- if the description of the tool is vague, claude has a chance to not pick it
		- example: get_customer ("retrieves customer info") and lookup_order ("retrieves order details"), prompt - "check my order #1234", claude picks get_customer
	- five elements of a good description
		- purpose - what does this tool do
		- input format - what should the input look like, include examples
		- output - what comes back
		- when to use - in what situation should claude use this tool
		- boundary - when should claude not use this tool 
	- bad vs good description
		- bad - name: analyze_content, desc: analyzes content, input: url: string
		- good - name: extract_web_result, desc: extracts structured data from web pages. Input: valid HTTPS url, Output: title, text, date. input: url: string
		- good description includes detailed explanation, examples, and where to not use this till
	- split generic into specific
		- analyze_document - could mean extract data, summarize, verify
		- it would be better to split such tool and use specific ones
		- extract_data_points, summarize_content, verify_claim_against_source
	- the system prompt keyword trap
		- system prompt "always analyze customer requests carefully"
		- two tools available analyze_content (analyzes content from url), lookup_order (retrieves order details by order id)
		- user prompt "whats the status of oder #123?"
		- claude picks analyze_content tool because of the word "analyze" in the system prompt
		- the fix - rename analyze_content to extract_web_content
		* system prompt names should not match tool names, it may cause claude to pick this tool 
	- tool naming strategies
		- action + object - extract_data_points
		- verb + scope - search_web_articles
		- domain-prefixed - billing_lookup_invoice
		* avoid generic verbs like process, handle, do
	- 5 anti-patterns
		- minimal descriptions - tool descriptions should include purpose, inputs, outputs, when to use
		- overlapping descriptions - each tool must have unique description, otherwise claude can pick any of such tools
		- generic tool names
		- system prompt keyword collisions - tool names should not match system prompt words
		- missing boundary conditions - state when not to use the tool, example - not for PDFs
	- 6 things to know
		- tool description is the primary mechanism how claude chooses the tool
		- five primary elements for tool description - purpose, input format, output, when to use, when not to use
		- split generic tools to specific tools
		- renaming ambiguous tools - dont chose generic names
		- system prompt keywords can make claude pick tools just by keyword matches
		- when exam shows misrouting problem - improve the description first
part - 10
	- domain 2 - task 2.2 - structured error responses for mcp tool
		- when a tool fails, it should return a structured response, not just text
		- example - "errorCategory": "transient", "isRetryable": true, "suggestion": "retry in 2 seconds"
	- the isError flag
		- this is a signal layer
		- when this flag is returned as true, claude know that its an error report, not success data
		- "type": "tool_result", "tool_use_id": "tool_891", "is_error": true, "content": "..."
		- without a structured body, claude guesses the recovery action
		- structured error body is decision layer
	- 4 error categories
		- transient - timeout, service down, agent waits and retries
		- validation - invalid input, agent fix the input and retry
		- business - policy volation, agent explains to user why it wont execute this tool
		- permision - unautharized access, escalates to user
	- 5 structured error fields
		- errorCategory - names failure type (transient, validation, business, permission)
		- isRetryable - true/false
		- message - technical detail for logging, not shown to user
		- customerMessage - what to tell the user, business errors only - must be polished and user friendly
		- suggestion - next action for the agent: retry, escalate to human, ask for correct input
	- access faiilures vs valid empty results
		- search_orders("1234) - tool call
		- isError: true, errorCategory: "transient", message: "DB connection timeout" - claude retries the call
		- isError: false, orders: [], total: 0 - claude tells user "you have no orders"
	- local recovery in subagents
		- local recovery - each subagent tries to handle error itself, if all attempts fail - it returns a structured error response to the coordinator
		- subagent should - retry locally, report with results and alternatives before escalating
		- subagent calls search_web("something") -> gets timeout -> retries locally 1 time -> if sucess returns result to coordinator, if not escalates with context
	- 5 anti-patterns 
		- generic errors - include errorCategory, isRetryable, suggestion
		- returning empty results for failures - an empty array tells the user that nothing exists when in reality it was timeout error
		- retrying business rule violations - set business rule violations as isRetryable: false
		- propagate all errors to the coordinator - handle transient errors locally in subagents
		- no partial results in error reports - always include what was attempted and alternatives exist
	- 6 things to know
		- 4 error categories - transient, validation, business, permission
		- 5 structure error fields - errorCategory, isRetryable, message, customerMessage, suggestion
		- access failures vs empty results
		- local recovery for subagent transient errors
		- isRetryable: false on business violations prevent wasted max_tokens
		- escalation reports - always include partial results and alternatives in escalation reports

part 13
	- domain 2 - task 2.5 - 6 built in tools
		- grep - search file contents
		- glob - find files by name / path pattern
		- read - load full file contents
		- write - create or completely overwrite a file
		- edit - targeted text replacement in existing file
		- bash - run shell commands
	- glob vs grep
		- glob - searches file names/paths - pattern **/*.test.php
		- grep searches file contents - pattern some_function()
	- two phase search strategy - grep then read
		- phase 1 - grep - find entry points (finds multiple files containing your phrase)
		- phase 2 - read - understand the found files
	- edit vs write
		- edit - makes a targeted text replacement, you provide a string and it changes the other string, used for replacing parcial parts
		- write - replaces entire file with new content, used to create new files or complete rewrites
		* when using edit, the haystack string must be unique, if theres multiple choices - provide additional content until its unique
	- read + write
		- when edit failes (cant find unique haystack) - use read + write
		- read the entire file
		- modify the edit mentally
		- write output the modified version
		* exam tests whats the fallback when edit fails
	- incremental exploration
		- dont read entire codebase
		- grep for entry point
		- read the route file
		- read the specific handler
		- read the billing service
		- in other words - only read stuff that matters, this manages the context window efficiently, this is called incremental exploration
	- 5 anti-patterns
		- reading all files upfront - this fills context window with irrelevent files, start with grep to find entry points, then read selectivly
		- using grep to find file names - use glob
		- using write to modify one line - use edit for small changes
		- using edit on non-unique match - include more surrounding context or fallback to read + write strategy
		- using bash for file search - built in grep and glob are more optimal
	- 6 things to know
		- grep searches file contents, glob searches file names and paths
		- search strategy - grep first, then read 
		- edit for targeted changes require unique match, write for new files or complete rewrides
		- edit fails on non-unique match - use fallback - read + write
		- incremental exploration - follow imports and functions calls step by step - dont read entire codebase
		- bash is for build, test, install, git - not for filesearch, use built in grep and glob tools
